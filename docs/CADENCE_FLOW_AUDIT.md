## Что совпадает в коде

| Этап | Comfy CPU / CUDA | Native Cadence |
|---|---|---|
| Яркость для flow | RGB → 0.299R + 0.587G + 0.114B, uint8 | Те же коэффициенты и преобразование |
| Уменьшение | Максимальная сторона 640, INTER_AREA | То же |
| Farneback | Два направления; 0.5 / 3 / 17 / 3 / 5 / 1.1 / 0 | То же |
| Возврат поля к исходному размеру | INTER_LINEAR, независимые множители ширины/высоты | То же |
| Деформация | Координаты `x − flow * amount`, border replicate | То же |
| Проверка обратного движения | Reverse field по `x + flow`, residual / (0.5 + 0.01 * magnitude), границы кадра | То же |
| Защита контуров | Минимум исходных и деформированных confidence обеих сторон | То же |
| Защита от новых расхождений | exp(−max(0, warped_difference − original_difference) / 0.03) | То же |
| Сглаживание confidence | CPU Gaussian 5×5, CUDA ядро [1,4,6,4,1]/16 в двух измерениях | OpenCV Gaussian 5×5 с sigma=0 |
| Итог | Смешивание деформированного и простого кадров по confidence | То же |
| Интеграция выдержки | Треугольные веса с минимумом 1e−4; flow до shake/усреднения | То же |

Comfy CUDA округляет координаты remap до 1/32 пикселя перед grid_sample; OpenCV INTER_LINEAR также использует табличную интерполяцию. Это не обнаруженная смена знака или отсутствие защиты в native. Побитовая идентичность разных версий OpenCV, NumPy/PyTorch и компиляторов без прогона не утверждается.

Native получает от VideoReader RGB в sRGB: вход gamma24/linear перед flow переводится в sRGB. Ошибка «flow считается в линейном свете, а Comfy в гамме» в прочитанном коде не обнаружена. Подготовленные flow-кадры одинаково поступают в CPU и CUDA capture; сам Farneback/warp в native остаётся CPU OpenCV. Native shake и RNG отличаются от Python-потоков Comfy, поэтому одинаковый seed не даёт побитового совпадения полной съёмки. Для изоляции flow сравнение выполняется без shake/оптики/кодека.

## Фактические настройки сравниваемых запусков пока не совпадают

Пользователь затем подтвердил точные настройки успешного Comfy: **source_fps=36, shutter_fraction=0.65, motion_blur_strength=0.5, blur_samples=9, compute_device=cuda**. Для сравнения в приложении Cadence нужен source_fps_mode=custom и source_fps=36; mode=timeline оставляет фактическое значение 25. Эти данные заменяют предположение о shutter=0.5 по repository workflow. Shake и прочие параметры успешного Comfy пользователь пока не уточнял; значения из примера ниже не следует выдавать за его фактические настройки.

При одинаковой скорости ручки ширина выдержки в индексах входных кадров пропорциональна source_fps × shutter_fraction × motion_blur_strength: Comfy даёт 11.7, последний native request — 12.5 (оба значения ещё делятся на скорость ручки). Поэтому нельзя объяснять проблему просто «вдвое большей motion_blur_strength»: полный множитель отличается примерно на 6.8%, а число/веса отсчётов и временные центры существенно различаются. Приоритетный cross-reference — --backend cuda, CPU нужен для разделения причин расхождения. Пользовательские настройки не менялись, прогон ещё не выполнен.

Из локальных сохранённых настроек и последнего `request.ini`/`result.ini` прочитано:

- Cadence: blur_samples=3, shutter_fraction=0.5, motion_blur_strength=1, camera_shake_strength=1, target_fps_min/max=18/22.
- Последний request: source_fps=25, output_fps=25; decoded encoded_source_fps=24. В настройках source_fps_mode=timeline; сохранённое custom=36 в этом режиме не используется.
- Сохранённый reference workflow `Видео-в-Хронику-по-этапам.json`: source_fps=36, blur_samples=9, shutter_fraction=0.5, motion_blur_strength=0.5, camera_shake_strength=0.5, target_fps_min/max=16/20. Другие примеры также используют 9 отсчётов, но имеют разные FPS. Это примеры из репозитория, а не подтверждённые параметры успешного запуска пользователя; точный workflow запрошен.

При 3 отсчётах нормированные веса приблизительно `[0.0001, 0.9998, 0.0001]`. Почти весь результат — один центральный дробный кадр flow. При 9 центральный вес около 0.25, остальные значимые отсчёты распределены по выдержке. Это свойство **обоих** алгоритмов: простое увеличение motion_blur_strength не исправляет вырожденные веса трёх отсчётов. Оно может объяснить большую видимость дефектов отдельной интерполяции, но причинная связь с пользовательским клипом ещё не подтверждена. Подсказка blur_samples дополнена этим пояснением. Сохранённые пользовательские настройки не изменялись.

## Независимое прямое сравнение

Добавлен `tests/compare_comfy_flow.py`. Он читает AST **реального** файла референса и загружает только определения функций flow/сэмплера, не запускает Comfy и не заменяет их переписанной формулой. Синтетические одинаковые float32 RGBA-кадры содержат неподвижный текстурированный фон, быстрый текстурированный объект и неподвижный объект перед ним. Проверяются перемещения 8/24/48 px, позиции 0.2/0.5/0.8 и размер 960×540 для пути уменьшения до 640.

Референсные результаты временно записываются вместе с исходными float-кадрами. Новый режим `silentfilm_cadence_flow_tests --compare-comfy <fixture>` запускает production FlowSampler на этих исходниках и выводит максимальную/среднюю абсолютную ошибку RGBA. Допуски: max 1e−3, mean 1e−5. Оба процесса печатают версию OpenCV. Несовпадение — основание исследовать численные различия/версии, а не автоматически считать, что верен один из backend. Обычный CTest сохраняет прежние проверки stationary/translation/cache/alpha; дополнительное сравнение запускается явно, потому что требует Python-пакеты референса.

Пользователь сначала собирает диагностический target системным CMake:

```bash
cmake --build build-cuda --target silentfilm_cadence_flow_tests --parallel 2
ctest --test-dir build-cuda -R '^silentfilm_cadence_flow$' --output-on-failure
```

Затем из Python-окружения, где уже работают Comfy NumPy/OpenCV/PyTorch (не требуется для обычной сборки/работы OFX), из корня этого проекта:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 tests/compare_comfy_flow.py --backend cpu
PYTHONDONTWRITEBYTECODE=1 python3 tests/compare_comfy_flow.py --backend cuda
```

Скрипт не читает пользовательское видео и не меняет референс, настройки, проект Resolve или результаты рендера. Временные файлы удаляются по завершении. Артефакты на реальном материале этим непрогнанным тестом не объявляются исправленными. Следующий шаг — получить вывод прямого сравнения и точный успешный Comfy workflow, затем сравнить одинаковые входные кадры, параметры и этап обработки.


## CUDA sampler — 2026-11-12

Подготовлены GPU warps/consistency/confidence/5×5 binomial blur/blend с квантованием координат1/32, border/reflect padding как ComfyCUDA. Farneback остаётся CPU. Production CUDA-путь не вызывает CPU sample(); он запрашивает поля через fields(), а деформированные отсчёты сразу передаёт captureCUDA вVRAM. Путь ещё не собран и не проверен.

Команды пользователя после сборки:

```bash
ctest --test-dir build-cuda -R 'silentfilm_cadence_flow' --output-on-failure
```

В существующем Python-окружении Comfy:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 tests/compare_comfy_flow.py --backend cuda --native-test build-cuda/silentfilm_cadence_flow_cuda_tests
```

Это сравнивает именно новый CUDA sampler с ComfyCUDA, прежний target без cuda в имени проверяет CPU sampler.
