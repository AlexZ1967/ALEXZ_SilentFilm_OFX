✅ **2026-11-10 — пользователь выбрал отдельное приложение и оптику в OFX.** Код 0.11 подготовлен; актуальный сценарий — [CADENCE_APP.md](CADENCE_APP.md). Нижеследующее исследование описывает основания выбора; запуск новых API/приложения пока не проверен.

✅ **2026-11-10 — изучены установленная документация SDK и официальное описание Resolve 21.** Это исследование API; приложение, сборки, тесты и скрипты не запускались. Пользователь сообщил об обновлении до Resolve 21; точный номер запущенного приложения не запрашивался. Наличие документации 21.1.2 не доказывает версию работающего процесса.

## Что изменилось

Локальный `/opt/resolve/Developer/Scripting/CHANGELOG.md` перечисляет новые возможности:

- **21.0.4:** `Timeline.GetSelectedClips()` — выбранные элементы таймлайна.
- **21.1:** `TimelineItem.GetSpeed()` / `SetSpeed()`.
- **21.1.2:** изменение левого/правого монтажного края, позиции элементов, перемещение элементов и копирование атрибутов, включая существующую временную карту.

В `/opt/resolve/Developer/Scripting/DaVinciResolveScript.pyi` класс `SpeedOptions` содержит `Percentage`, `PitchCorrection`, `StretchKeyframesToFit`, `RippleTimeline`. `SetSpeed()` принимает этот словарь. Это документированный способ управления скоростью через scripting API, которого не было в прочитанной документации 20.2. Поведение в текущем проекте ещё не проверено. Параметры не содержат списка точек переменной скорости.

`CopyAttributesOptions.retimeEffect` позволяет копировать уже существующую speed timemap, а `rippleSequence` — сдвигать последовательность после вставки карты. Это не документированный способ построить произвольную карту из нашего расписания экспозиций.

Официальный [New Features Guide Resolve 21](https://documents.blackmagicdesign.com/SupportNotes/DaVinci_Resolve_21_New_Features_Guide.pdf), страницы 62 и 96, описывает улучшенное редактирование кривых retime с Bezier easing и OpenFX 1.5 Color Management APIs. Первое относится к интерфейсу редактора, второе — к обработке цвета. Эти изменения сами по себе не предоставляют OFX управление монтажной длительностью.

## Ограничения и варианты

В поставленном OpenFX SDK заголовок `OpenFX-1.4/include/ofxImageEffect.h` описывает `GetTimeDomain` только для General context; в остальных контекстах длительностью управляет хост. Наличие action не доказывает, что Resolve автоматически изменит Edit-клип по ответу плагина. Поддержка такого сценария в Resolve 21 не подтверждена.

`/opt/resolve/Developer/Workflow Integrations/README.txt` по-прежнему указывает Windows/macOS для Electron-плагинов и отсутствие поддержки Linux. Это ограничение поставленной документации; работоспособность такой панели под Linux не проверялась.

Для Linux возможен интерфейс отдельного приложения, которое обращается к Resolve через внешний Python scripting API. Тогда пользователю не потребуется вводить Lua в Console. Это вариант архитектуры, ещё не реализация: потребуются настройка external scripting, проверка подключения и отдельный выбор GUI. Python должен оставаться в отдельном процессе, без зависимости OFX от Python/ComfyUI. Native CLI/GPU-ядро можно сохранить.

Новый `SetSpeed` полезен для постоянной скорости и потенциальной автоматизации согласования монтажной длины, но не заменяет расчёт M физических экспозиций с выдержкой, экспозицией, shake и focus. Повторное ускорение нормированного OFX-выхода нельзя объявлять точной проекцией кадр-в-кадр без проверки временной выборки.

Следующий шаг: выбрать удобный интерфейс без Console/Lua и подготовить отдельный пользовательский сценарий проверки `SetSpeed` на копии таймлайна. Если нужен полный физический каденс уже сейчас, подтверждённый путь остаётся native-пересчётом M экспозиций и импортом результата; интерфейс запуска и импорта можно заменить независимо от математики.

## Разделение Camera и вариант Fusion

Пользователь предложил оставить параметры Camera без влияния на длительность в OFX, а каденс вынести в окно приложения. Рабочее направление: приложение отвечает за расписание вращения ручки, M кадров, выдержку/временную интеграцию, связанную с FPS экспозицию и движение камеры внутри выдержки. OFX отвечает за доступные для интерактивной настройки оптические параметры. Перенос требует сохранить порядок операций и исключить повторную обработку: текущий CLI запекает полную Camera. Нельзя просто включить вторую Camera поверх готового результата. Фокус должен использовать номер физической экспозиции и согласованный seed; если оставлять его в OFX, надо определить привязку при подрезке и перемещении клипа.

Fusion TimeStretcher позволяет задавать соответствие выходного кадра исходному через Source Time. Это не полноценная модель физической выдержки с движением камеры внутри неё. Длительность Fusion Composition можно менять на Edit, но это отдельная монтажная операция; автоматическое изменение Edit-длины из собственного узла не подтверждено. Официальная [страница Fusion 21](https://www.blackmagicdesign.com/products/fusion/) описывает адаптацию анимации к изменению длины клипа, а не обратное управление монтажом узлом. [Учебник Blackmagic](https://documents.blackmagicdesign.com/UserManuals/DaVinci-Resolve-18-Fusion-Visual-Effects.pdf) описывает Change Clip Duration для Fusion Composition; это более ранний документ, не доказательство новых API версии 21. Поэтому Fusion можно рассматривать как альтернативный интерфейс/контейнер, но пока нельзя обещать, что он устранит необходимость согласования монтажной длины.
